# motionhub/motions

The open motion format and the public catalogue behind motionhub.dev. Read [README.md](README.md), then [SPEC.md](SPEC.md).

- **SPEC.md only grows.** A change never alters the meaning of what a published version says; it adds, under a new `spec` version. What only one tool needs stays in that tool's directory and `x-<tool>` members (SPEC.md §7) until several tools share it.
- **The rules live in one place as code:** `tools/check.mjs` and its portable `tools/security/` modules (format and hub rules, no dependencies) with its tests in `tests/`. A rule written in SPEC.md or CONTRIBUTING.md and not in the checker is a bug, and the other way round.
- **English** for everything a developer reads: code, comments, documents, commit messages. A motion's own `MOTION.md`, translations and descriptions are in whatever language its author chooses (SPEC.md §8).
- **A published motion never changes under its version** (SPEC.md §9): any change to a file in a motion, a component included, comes with a higher `version` in its `motion.json`, or deploy refuses to replace the published package.
- **One author per hub motion.** `authors` has exactly one entry. Updates keep the same numeric account id; no implicit transfers or co-author permissions. Credit help in `CREDITS.md`.
- **Accounts, not logins, own motions.** `accounts/<login>.json` records each login a motion names with its GitHub account's numeric id, once; ownership and scope are checked by that id (CONTRIBUTING.md, "Accounts"). A record is never changed or removed.
- **Every commit is signed off** (`git commit -s`); the checks refuse a pull request without it.
- **Who may change what is judged by main**: `.github/workflows/ownership.yml` runs on `pull_request_target` (always main's copy) with main's checker over the pull request's files as data. Keep it that way: never run the pull request's code there, never give it a secret beyond the read-only `GITHUB_TOKEN`, nor a write permission.
- **The brand lives in `brand/`** ([brand/BRAND.md](brand/BRAND.md)): a colour, size or font is decided in `brand/brand.tokens.json` and nowhere else, and the site is quiet so the motions can be loud.
- Before pushing: `npm test`, `node tools/check.mjs` and `node tools/build.mjs`; for a change to a package with its own tests (`packages/runtime`, `packages/remotion`), `npm test` there too; for a change to the runtime, the player or a reel, `npm ci` and `npm run build` in `player/` after `node tools/build.mjs`, then `npm run smoke` there (`node player/render.mjs <id>` renders a reel's video to `player/.cache/render/`).
- **motionhub.dev's site is not in this repository.** Its pages, Worker, database and deploy are in the private `motionhub-dev/motionhub-web`, which builds over this repository at a pinned commit (HUB.md, "Where things are"). It takes `tools/build.mjs` (with an output directory), `tools/site.mjs`, `tools/docs.mjs`, `tools/check.mjs`, `tools/security/` (no dependencies, not even Node's: its Worker bundles them), `tools/release.mjs`, `brand/` and `player/` (with `MOTIONHUB_DIST`; `player/reel-plugin.mjs` also runs in its pages, in a browser, to preview a private motion's reel, and `/play/_preview/` plays it): keep what they offer working from outside, and say in the pull request when it changes. A path `site/…` in a comment or document names a file there.
- **The docs at motionhub.dev/docs are the repository's own documents** (`tools/docs.mjs` lists them): change a document where it lives, and write a guide that has no home yet in `docs/`. A link between documents is a relative path to the file, which the docs turn into a page or its Markdown twin.
- **Dependencies stay where they are used.** The repository's root is the zero-dependency `@motionhub/cli` package; the reel players have their own `package.json` and lockfile in `player/`.
- **Claude on GitHub.** Maintainer-triggered `@claude` and `/review` use tool-free API inference and a separate fixed comment publisher. Model output is advice and optional patch data, never authorization or executed code. Activation, credentials, branch rules and recovery are described in [docs/security.md](docs/security.md).
